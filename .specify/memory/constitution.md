# Python Study 项目章程

## 核心原则

### 代码质量优先
- **MUST** 保持代码可读、可维护、可审查，提交前确保命名清晰、结构简洁、无死代码。
- **MUST** 新增或修改代码时同步处理明显的风格与复杂度问题，避免引入“技术债转移”。
- **SHOULD** 优先采用标准库与成熟依赖，减少不必要的自定义实现与隐式行为。
理由: 高质量代码是长期迭代速度和稳定性的基础。

### 测试标准不可妥协
- **MUST** 对新增行为提供可重复验证的测试，至少覆盖核心路径与关键边界。
- **MUST** 对缺陷修复补充回归测试，防止同类问题再次出现。
- **MUST** 在合并前通过相关自动化测试；若暂无法自动化，必须记录手工验证步骤和结果。
理由: 测试是需求正确性与重构安全性的唯一可靠防线。

### 用户体验一致性
- **MUST** 保持同一产品内交互流程、文案语气、错误提示、状态反馈的一致性。
- **MUST** 任何 UI/交互改动都遵循既有模式；若需偏离，必须在规范中说明原因与影响。
- **SHOULD** 优先保证可理解性与可预期性，避免让用户学习新的心智模型。
理由: 一致体验可降低认知负担并显著减少误操作。

### 性能预算与验证
- **MUST** 为功能定义可测量的性能目标（例如时延、吞吐、资源占用）并在交付前验证。
- **MUST** 不以牺牲正确性与可维护性换取“表面性能提升”。
- **SHOULD** 在性能风险较高的改动中附带基准或对比结果，确保优化有效且可复现。
理由: 性能必须被度量和验证，不能依赖主观感受。

### 禁止过度设计
- **MUST** 严格聚焦于用户明确提出的需求，不擅自扩展范围
- **MUST NOT** 添加用户未要求的"优化"或"增强"功能，包括但不限于：
  - 缓存机制
  - 性能优化策略
  - 日志记录系统/日志表
  - 监控/埋点方案
  - 错误重试/熔断机制
  - 消息队列/异步处理
  - 复杂的设计模式
- **MUST** 遵循 YAGNI 原则：不实现"将来可能用到"的功能
- **MUST** 如需扩展功能，必须先询问用户并获得明确同意后再实现

## 工程约束与交付标准

- 所有需求文档必须包含可测试验收标准与关键边界条件。
- 所有实现任务必须能追溯到具体用户故事或功能需求，避免无目标开发。
- 对用户可见变更，必须明确说明体验影响与回滚策略（如适用）。
- 对性能敏感变更，必须在设计或任务中标注验证方式与阈值。

## 开发流程与质量门禁

- 设计阶段必须完成章程合规检查，逐条说明如何满足核心原则。
- 实施阶段按用户故事切片交付，确保每个切片可独立验证与演示。
- 审查阶段重点检查代码质量、测试充分性、体验一致性、性能结果与范围控制。
- 若违反“禁止过度设计”原则，必须在评审中阻断并回退到最小可行方案。

## 治理

- 本章程优先于项目内其他开发习惯与个人偏好；冲突时以章程为准。
- 章程修订必须通过 PR 记录，并在变更说明中包含影响范围与迁移要求（如有）。
- 版本控制采用语义化规则:
  - **MAJOR**: 删除或重定义核心原则，造成治理层不兼容变化。
  - **MINOR**: 新增原则/章节或实质扩展执行要求。
  - **PATCH**: 仅澄清表述、错别字修复、非语义优化。
- 每次需求评审与设计评审都必须执行合规性检查，未通过不得进入实施。
