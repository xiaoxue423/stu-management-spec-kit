# 功能规范: 学生与成绩数据持久化

**功能分支**: `feature/SPEC-202604031050/005-mysql-db-persistence`
**创建时间**: 2026-04-03
**状态**: 草稿
**输入**: 用户描述: "把内存存储替换成真实 DB MySQL 在已有的 spec目录下面做调整"

## 关联范围

本规范在 `specs/001-student-score-management`、`specs/002-add-student-score-entry`（及前端组件相关 `003`）已定义的业务能力之上，约束**数据保存方式**：由进程内临时存储改为通过真实数据库持久保存。具体数据库产品与连接方式见本文「用户直接提供的技术细节」。除持久化与由此带来的可靠性、运维配置要求外，不重定义列表、录入、编辑、接口边界等既有需求。

## 用户场景与测试 *(必填)*

### 用户故事 1 - 重启后仍能查看历史数据 (优先级: P1)

作为 教务老师，我想要 在系统维护重启或重新部署之后仍能看到此前录入的学生与成绩，以便日常业务不依赖“会话期内不关机”的隐含前提。

**优先级原因**: 若内存存储，数据在服务重启后即丢失，直接违背“学生管理系统”的基本预期，阻断业务连续性。

**独立测试**: 录入若干学生与可选成绩后，执行一次完整的后端进程重启（或等价的服务停止再启动），再次打开学生列表与任一学生详情，核对原数据是否完整可见。

**验收场景**:

1. **当** 用户已在系统中成功创建或编辑过学生与成绩记录 **后** 学生管理系统 **应当** 在一次常规服务重启后仍展示相同的学生列表与成绩内容。
2. **如果** 重启前某学生仅有基本信息、尚无成绩 **则** 学生管理系统 **应当在** 重启后 **继续** 正确展示该学生及其“无成绩/待补录”状态，与重启前一致。
3. **在** 并发多用户持续开展录入与查询 **期间** 学生管理系统 **应当在** 正常运维窗口内的重启后 **不丢失** 已提交的写入结果。

---

### 用户故事 2 - 多实例部署下数据一致 (优先级: P2)

作为 系统运维方，我想要 在需要横向扩展或多副本部署时各请求读到同一套学生与成绩数据，以便避免“各进程各自一份名单”造成的混乱。

**优先级原因**: 内存存储天然无法在多实例间共享；迁往共享的持久化数据库后才能在合理架构下满足一致读写的业务预期。

**独立测试**: 若存在两个及以上后端实例（或文档化说明如何通过单实例验证“共享存储”语义），向实例 A 写入后，经实例 B 查询应得到同一结果（在文档化的一致延迟边界内）。

**验收场景**:

1. **当** 多个后端实例指向同一套数据库配置并对外提供服务 **时** 学生管理系统 **应当** 使得任一实例上的列表与详情查询反映已提交的写入，不出现仅限单进程可见的“幽灵数据”。
2. **如果** 某写入因数据库不可用而失败 **则** 学生管理系统 **应当** 向用户给出可理解的失败反馈，且不声称已成功保存。

---

### 用户故事 3 - 可追溯的交付与配置 (优先级: P3)

作为 开发人员或运维人员，我想要 具备可重复的库连接与结构初始化说明，以便新环境能在约定步骤内具备与验收一致的持久化能力。

**优先级原因**: 降低环境搭建成本，减少“同事机器上能跑、测试环境无库”类问题。

**独立测试**: 按项目内 `quickstart` 或等价文档从零启动依赖已配置数据库的环境，完成最小读写验收。

**验收场景**:

1. **当** 按文档完成数据库准备并启动应用 **时** 学生管理系统 **应当** 能建立连接并完成与当前模型匹配的持久化读写。
2. **在** 连接参数错误或服务不可达 **处** 应用 **应当** 以可诊断的方式记录或提示失败原因，避免无声失败。

---

### 边界情况

- 当数据库连接短暂闪断后恢复时，系统如何对待进行中的请求与重试策略？
- 当磁盘或库满、权限不足时，用户提交写入会看到什么反馈？
- 当从内存实现迁移到目标数据库时，是否要求一次性数据迁移脚本（若无历史生产数据，可明确为“无迁移，仅新环境落库”）。

## 需求 *(必填)*

### 功能需求

- **FR-001**: 系统必须将 `001`/`002` 规范所涉学生档案与月考成绩业务数据写入持久存储，使得常规进程停止与启动后，查询结果与停止前已成功提交的数据一致。
- **FR-002**: 系统必须确保同一学号、成绩等业务规则在持久化后仍成立（例如学号唯一、与既有验收场景一致），不因存储介质变更而弱化校验。
- **FR-003**: 当持久存储不可用或写入失败时，系统必须向调用方返回明确的失败语义，且不得在界面上表现为“成功保存”而实际未落库。
- **FR-004**: 系统必须提供可文档化的方式（连接信息、迁移或建表步骤等），使新环境能在约定配置下完成落库读写，并与现有接口契约兼容。
- **FR-005**: 系统不得在仅重启后端服务的场景下丢失已成功提交的学生与成绩数据。

### 非功能需求 *(必填)*

- **NFR-001 代码质量**: 变更后的代码必须保持可读、可维护，并通过既定质量检查。
- **NFR-002 测试标准**: 关键路径（写入—重启—查询）必须可自动化或脚本化复现验证。
- **NFR-003 体验一致性**: 用户可见交互与 `001`/`002`/`003` 规范一致；持久化失败时的提示需清晰、可行动。
- **NFR-004 性能要求**: 在正常局域网或单机联调环境下，针对已定义的数据规模目标（沿用 `001` 中列表与搜索性能叙述或同等量级的抽样验证），95% 的列表与只读查询在完成迁库后不应劣于迁库前的可感知体验；若出现回gress，须在交付说明中记录原因与补救计划。
- **NFR-005 范围控制**: 不引入与持久化无关的大规模重构；不实现读副本、分库分表、异地多活等未被本需求驱动的能力。

### 关键实体 *(如果功能涉及数据则包含)*

- **持久化学生档案**: 与 `002` 中“学生档案”语义一致，需落库并可在重启后检索。
- **持久化月考成绩记录**: 与 `002` 中“月考成绩记录”语义一致，与学生档案的关联在重启后保持有效。

## 成功标准 *(必填)*

### 可衡量的结果

- **SC-001**: 在验收脚本或检查表中，连续执行「创建/编辑—服务重启—列表与详情核对」三个步骤，100% 用例下可见数据与重启前一致（排除已文档化的不达标修复项）。
- **SC-002**: 在抽样验收中，针对至少 10 条有成绩与 10 条仅有基本信息的记录，重启后检索准确率 100%。
- **SC-003**: 运维或开发按文档首次搭建持久化环境的成功率（一次通过连接与读写验证）不低于 90%，或在二次以内根据文档排障成功。
- **SC-004**: 上线后观察期内，无“重启丢数”或“误以为已保存实际未落库”的未解决工单（或等价沟通记录为零）。

## 用户直接提供的技术细节 *(如果存在的话则包含，且无信息损失)*

- **数据库产品**: MySQL。
- **改造方向**: 将当前内存存储替换为真实 MySQL 数据库访问层，`specs/001-student-score-management` 与 `specs/002-add-student-score-entry` 目录下规范同步体现持久化约束（见各 spec 内增补说明）。
- **官方参考**（组件/生态）: 选用与项目栈匹配的 MySQL 驱动与迁移/ORM 实践，以仓库内既有 Python 技术栈为准。

## 假设

- 运行环境可提供受控的关系型数据库实例（版本在团队约定范围内），网络与账号权限满足应用连接。
- 当前无必须保留的“仅存在于内存中的生产数据”；若有，将通过一次性导出/导入或接受数据从零开始（若与用户冲突，需在实施前单独确认）。
- 接口路径与前端契约与迁库前的 `001`/`002` 保持一致，除非另有专项变更说明。

## 范围守卫 *(必填)*

- 本次不实现: 多租户隔离、字段级审计日志、跨库同步、实时备份演练界面、数据库控制台嵌入。
- 若需新增能力: 任何超出“用真实数据库持久化替代内存并在 `001`/`002` 范围内保持行为一致”的改动，须单独拉需求与验收标准。
